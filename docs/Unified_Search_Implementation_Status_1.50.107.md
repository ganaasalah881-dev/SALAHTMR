# تقرير تنفيذ توحيد البحث — الحالة بعد التعديلات

**المرجع السابق:** جرد ما قبل التنفيذ في `Unified_Search_Audit_PreImplementation_1.50.107.md`، وقد عُرض للمستخدم قبل تعديل الكود.

## ما تم تنفيذه

تم توسيع `DocSearchWindow` ليصبح مسار الاختيار الموحد: حقول معيار خاصة بالشاشة مع قيم أولية، عرض تلقائي، عرض الكل، بحث سريع عبر الأعمدة، فرز، تنقل أول/سابق/تالٍ/أخير، فتح بالزر أو بالنقر المزدوج، وإرجاع رقم السجل. عند فشل مزود البيانات تُمسح النتائج القديمة وتظهر رسالة صريحة بدلاً من إبقاء نتائج قديمة كأنها حديثة.

| الشاشة / الوظيفة | مسار البحث بعد التعديل | كيف يرجع الاختيار للشاشة الأصلية |
|---|---|---|
| أوامر الإنتاج | نافذة أوامر مشتركة بدل DataGrid مخصصة؛ تستدعي `IProductionOrderService.SearchOrders` | `ShowOrderInPlace(id)` يعيد المستند وتفاصيله إلى `OrderDocumentPanel` داخل شاشة الأوامر |
| الخطط `PlanningView` | استبدال `PlanSearchWindow` بـ `DocSearchWindow`؛ تُحدّث القائمة من DB قبل فتح النافذة | `OpenPlan(id)` في شاشة التخطيط نفسها |

| سجل التدقيق | زر «تطبيق» يفتح بحثاً مركزياً بمعايير المستخدم/الإجراء/الشاشة/المستند/الفترة، مع إبقاء الترقيم على الخادم | إعادة عرض الصفحة المناسبة وتحديد سجل التدقيق المختار في الجدول الأصلي؛ التفاصيل تبقى بالنقر المزدوج |

### تصحيح إتاحة الأوامر القديمة
كان `SearchOrders` يحصر النتائج بأحدث 400 أمر قبل تطبيق كلمة البحث، ما يمنع الوصول لأمر أقدم حتى برقم معروف. نُقل تطبيق شرط الرقم/العميل إلى الاستعلام قبل الحد الأعلى، مع دعم حتى 10,000 نتيجة للنافذة. أضيف اختبار خدمة يثبت العثور على سجل أقدم من نافذة الـ400 السابقة.

## الاستثناءات الوظيفية الموثقة

هذه المرشحات ليست بحثاً عن مستند محفوظ مطلوب فتحه؛ إبقاؤها محلياً مقصود ولا يبرر إنشاء نوافذ مستندات زائفة:

- `ReportsView`: البحث في معرض تعريفات التقارير، والبحث السريع داخل ناتج التقرير.
- `PlanningRequirementsView`, `ShipmentReportView`, و`SupplierMovementReportView`: فلاتر تحليل/معاينة للتقرير لا اختيار مستند تشغيلي.
- `PermissionsView.TreeSearchBox`: تصفية عقد شجرة الوحدات والشاشات، لا سجل مستخدم أو مستند؛ بحث المستخدم نفسه صار مركزياً.
- أزرار الاختيار المتخصصة للصنف/الدفعة/المورد في سياق إدخال مستند، وزر تفاصيل المخرجات الثانوية: اختيار lookup أو عرض تفاصيل لا بحث مستند.

## التحقق المنفذ والقيود

- بناء `DatesErp.Desktop.csproj --no-restore`: **نجاح، 0 أخطاء**؛ ظهرت تحذيرات موجودة عن `ThemeSettingsView.Tag` و`PlanningView._autoSaveTimer`.
- `UnifiedSearchContractTests` + `OrdersScreenToolbarTests`: **9 ناجحة، 0 فاشلة**. الاختبار الجديد يتحقق بنيوياً من تغطية المسارات التشغيلية، واختبار خدمة البحث عن أمر قديم اجتاز.
- مجموعة تحقق مركزة أوسع (مع `InspectionScreenTests`, `ProductionOrderScreenTests`, `PermissionGatingTests`): **44 ناجحاً و4 إخفاقات**. الإخفاقات: `PermissionGatingTests.Existing_Matrix_Is_Upgraded_For_Designated_Planning_Edit_Roles` (تعدد نتائج في `Single`)، اختبارا `ProductionOrderScreenTests` لسياق الطاقة/تعدد العملاء، واختبار `InspectionScreenTests.Screen_Code_Contains_No_Hardcoded_ResultType_Names_Or_Units` الذي يعتبر وجود «منسم» في واجهة الجودة قيمة ثابتة ممنوعة. لا نعتبر هذه المجموعة ناجحة بالكامل، ولم تُغيّر صلاحيات أو قواعد الجودة لتجاوزها.
- لا يمكن في بيئة Linux الحالية تشغيل واجهة WPF تفاعلياً؛ لذلك لم يُنفّذ اختبار يدوي على كل شاشة باتصال DB حقيقي، ولا يجوز إعلان استيفاء اختبار السجلات القديمة/الجديدة والصلاحيات والإضافة/التعديل/الحفظ على مستوى كل شاشة. الاختبار الجديد للخدمة يثبت فقط حالة الأمر الأقدم، وليس جميع تدفقات UI.

## الحالة

تنفيذ التوحيد البرمجي للمسارات التشغيلية المرصودة مكتمل مبدئياً والبناء ناجح، لكن **قبول التشغيل الشامل غير مُغلق** إلى حين تشغيل نسخة Windows أمام قاعدة اختبار والتحقق من كل شاشة، وبالأخص النتائج القديمة والجديدة، صلاحيات العرض والتعديل، فتح التفاصيل داخل نفس الشاشة، وعدم التأثير في الإضافة والتعديل والحفظ. لم تُبنَ أو تُستبدل أي حزمة إصدار تاريخية.
